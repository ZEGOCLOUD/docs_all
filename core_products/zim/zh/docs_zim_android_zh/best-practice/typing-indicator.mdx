# ZIM 正在输入（Typing Indicator）最佳实践

## 1. 功能简介

「正在输入…」状态提示（Typing Indicator）让接收方感知到对方正在编辑消息，减少"等待回应"的焦虑，是提升沟通实时感的关键细节。

核心设计约束：typing 是**瞬时状态而非消息**——它不应进入历史消息、不应产生留痕、不应出现在会话列表的最新消息展示中。基于该约束，本方案采用**信令消息（ZIMCommandMessage，type = 2）**实现，而非可存储的消息类型。

## 2. 消息类型选型

| 消息类型 | type | 是否可存储为历史消息 | 限频（单客户端） |
|-|-|-|-|
| 信令消息 ZIMCommandMessage | 2 | 不可存储 | 30 次/秒（间隔 34ms） |
| 弹幕消息 ZIMBarrageMessage | 20 | 不可存储 | 无限制（仅房间） |
| 文本消息 ZIMTextMessage | 1 | 可存储 | 10 次/秒（间隔 100ms） |
| 自定义消息 ZIMCustomMessage | 200 | 可存储 | 10 次/秒（间隔 100ms） |

选型结论：**必须使用信令消息（type = 2）**。信令消息不可存储，天然无留痕；不进入历史消息与会话最新消息展示；支持 30 次/秒的更高发送频率；不保证送达与顺序的语义与 typing 的瞬时状态完全匹配（丢包不影响体验）。

<Tip>

常见错误：使用自定义消息（type = 200）承载 typing。自定义消息属可存储消息，会导致 typing 信号进入历史消息列表、出现在会话列表的最新消息展示中，所以在接入时务必确认消息类型为 type = 2。

</Tip>

## 3. 机制设计

### 3.1 信令内容设计

信令消息的 message 字段为二进制数据，业务侧需要自行序列化，消息可以用一个 json 串来表示，下面是一个示例：

```json
// 正在输入（含保活心跳）
{ "bizType": "typing", "action": "typing", "ts": 1725000000000 }
// 停止输入
{ "bizType": "typing", "action": "stop", "ts": 1725000005000 }
```

| 字段 | 说明 |
|-|-|
| bizType | 业务标识，固定 "typing"，用于与其他业务信令区分 |
| action | typing（输入中）/ stop（停止） |
| ts | 时间戳，接收端可用于防乱序（信令不保证顺序） |

### 3.2 发送节奏（推荐值）

| 策略 | 参数 | 说明 |
|-|-|-|
| 首条立即发送 | 用户输入第一个字符时 | 保证提示快速出现 |
| 保活心跳 | 持续输入期间每 3 秒一次 | 对抗丢包；即使丢 1\~2 条也能被下一条补上 |
| 停止信号 | 停止输入 1 秒后 / 输入框失焦 / 清空 | 主动通知对端隐藏 |
| 发送节流 | 两次发送间隔 ≥ 34ms（30 次/秒限频） | 保活 3 秒的节奏远低于限频，无需额外处理 |

### 3.3 接收端展示与兜底

| 状态 | 触发条件 | UI 表现 |
|-|-|-|
| 隐藏 | 初始状态 / 收到 action: stop | 无提示 |
| 展示中 | 收到 action: typing | 展示"对方正在输入…" |
| 超时隐藏 | 距最后一条 typing 信号超过 10 秒 | 自动隐藏 |

超时兜底是必须的：stop 信号同样是不可靠信令，一旦丢失，接收端的"正在输入…"会永久停留。10 秒超时（远大于 3 秒保活间隔）保证状态最终收敛。

## 4. 接入示例

### 4.1 Android

```java
// 构造 typing 信令并发送（信令消息为二进制，需自行序列化）
String payload = "{\"bizType\":\"typing\",\"action\":\"typing\",\"ts\":" + System.currentTimeMillis() + "}";
ZIMCommandMessage commandMessage = new ZIMCommandMessage();
commandMessage.message = payload.getBytes();

ZIMMessageSendConfig config = new ZIMMessageSendConfig();
config.priority = ZIMMessagePriority.LOW;   // 低优先级，避免抢占业务消息的发送队列

zim.sendMessage(commandMessage, toUserID, ZIMConversationType.PEER, config, new ZIMMessageSentCallback() {
    @Override
    public void onMessageAttached(ZIMMessage message) {}

    @Override
    public void onMessageSent(ZIMMessage message, ZIMError errorInfo) {
        // typing 丢失不影响主流程，失败静默处理
    }
});

// 接收端：仅处理信令消息，反序列化后按 action 更新 UI，10s 超时兜底
zim.setEventHandler(new ZIMEventHandler() {
    @Override
    public void onMessageReceived(ZIM zim, ZIMMessageReceivedEventResult result) {
        for (ZIMMessage msg : result.messageList) {
            if (msg.getType() != ZIMMessageType.COMMAND) continue;
            ZIMCommandMessage cmd = (ZIMCommandMessage) msg;
            String payload = new String(cmd.message, StandardCharsets.UTF_8);
            // JSON 解析后：action = typing 展示、action = stop 隐藏；发送者用 msg.senderUserID 获取
        }
    }
});
```

### 4.3 Web

发送端：

```typescript
const TYPING_HEARTBEAT = 3000;  // 保活心跳间隔 3s
const STOP_DELAY = 1000;        // 停止输入判定延迟 1s
let heartbeatTimer: number | null = null;
let stopTimer: number | null = null;
let isSending = false;

// 构造 typing 信令并发送
function sendTypingSignal(toUserID: string, action: 'typing' | 'stop') {
  const payload = JSON.stringify({ bizType: 'typing', action, ts: Date.now() });
  // 信令消息 message 为二进制字段，需自行序列化
  const bytes = new TextEncoder().encode(payload);
  const commandMessage: ZIMCommandMessage = {
    type: 2,      // 信令消息：不可存储，避免留痕（关键！勿用 200 自定义消息）
    message: bytes,
  };
  const config: ZIMMessageSendConfig = { priority: 1 }; // 低优先级
  zim.sendMessage(commandMessage, toUserID, 0 /* 单聊:0 群组:2 房间:1 */, config)
    .catch(() => { /* typing 丢失不影响主流程，静默处理 */ });
}

// 输入中：立即发首条，随后 3s 保活
function onUserTyping(toUserID: string) {
  if (stopTimer) { clearTimeout(stopTimer); stopTimer = null; }
  if (!isSending) {
    isSending = true;
    sendTypingSignal(toUserID, 'typing');            // 首条立即发送
    heartbeatTimer = window.setInterval(() => {
      sendTypingSignal(toUserID, 'typing');          // 3s 保活，抗丢包
    }, TYPING_HEARTBEAT);
  }
}

// 停止输入：清保活，发 stop
function onUserStopTyping(toUserID: string) {
  if (stopTimer) clearTimeout(stopTimer);
  stopTimer = window.setTimeout(() => {
    if (heartbeatTimer) { clearInterval(heartbeatTimer); heartbeatTimer = null; }
    isSending = false;
    sendTypingSignal(toUserID, 'stop');
  }, STOP_DELAY);
}

inputElement.addEventListener('input', () => onUserTyping(toUserID));
inputElement.addEventListener('blur',  () => onUserStopTyping(toUserID));
```

接收端：

```typescript
const TYPING_TIMEOUT = 10000;   // 10s 超时兜底
const timeoutMap = new Map<string, number>();

zim.on('messageReceived', (zim, { messageList }) => {
  for (const msg of messageList) {
    if (msg.type !== 2) continue;                  // 仅处理信令消息
    let payload: any;
    try {
      payload = JSON.parse(new TextDecoder().decode(msg.message as Uint8Array));
    } catch { continue; }                          // 非本业务信令，忽略
    if (payload.bizType !== 'typing') continue;
    if (payload.action === 'typing') {
      showTypingIndicator(msg.senderUserID);
      resetTimeout(msg.senderUserID);              // 重置 10s 兜底
    } else if (payload.action === 'stop') {
      hideTypingIndicator(msg.senderUserID);
      clearTimeout(timeoutMap.get(msg.senderUserID)!);
    }
  }
});

function resetTimeout(userID: string) {
  clearTimeout(timeoutMap.get(userID)!);
  timeoutMap.set(userID, window.setTimeout(() => {
    hideTypingIndicator(userID);                   // 超时隐藏，防 stop 丢包残留
  }, TYPING_TIMEOUT));
}
```

Android / iOS / macOS / Windows / Flutter / uni-app 等平台均使用 ZIMCommandMessage（type = 2）与同一 sendMessage 接口实现，仅二进制序列化方式与语言层存在差异。

## 5. 群聊场景扩展（建议）

- 小群启用：群成员 ≤ 50 时启用；大群建议关闭，或仅对"最近活跃成员"展示；
- 接收端聚合：按 senderUserID 维护多份状态，可展示"张三、李四正在输入…"；
- typing 为不可存储信令，不产生历史消息存储开销；但会占用共享的信令限频额度（见第 6 节），多人高频输入时建议降低保活频率（如 3s → 5s）或设置独立降级开关。

## 6. 接入最佳实践

- **消息类型选择**：必须用信令消息 type = 2。禁止用自定义消息（200）或文本消息承载 typing，否则会产生留痕并污染会话列表。
- **必须做超时兜底**：10s 超时隐藏，防止 stop 丢包导致提示永久残留。
- **保活而非节流优先**：信令不可靠，用 3s 保活心跳对抗丢包。
- **离线天然不打扰**：信令不可存储，离线用户上线后不会收到过期 typing，无需额外处理。
- **限频额度是共享的**：30 次/秒的信令限频为单客户端共享额度，房间 / 群聊场景若同时用信令做上下麦、送礼等业务，typing 保活会挤占额度，建议降频或做独立降级开关。
- **多端登录过滤**：同一账号多端登录时，其他端也会收到自己的 typing 信令，接收端应过滤发送者为自己（senderUserID 为自己）的信令。

## 7. 效果验证

| 场景 | 预期表现 |
|-|-|
| A 输入文字 | B 立即看到"对方正在输入…" |
| A 持续输入 | 每 3s 保活一次，提示持续显示 |
| A 停止输入 | 1s 后发送 stop，B 的提示隐藏 |
| stop 信号丢失（弱网） | B 在 10s 超时后自动隐藏提示（关键验证项） |
| 历史消息检查 | A、B 双方翻看历史消息，均看不到任何 typing 记录（关键验证项） |
| 会话列表检查 | 会话列表最新消息不被 typing 污染（关键验证项） |
| 离线用户 | 离线期间不收到 typing；上线后不收到过期 typing |
| 群聊（小群） | 多位成员输入时分别展示各自状态 |

## 8. 常见问题

**Q1：为什么不能用自定义消息实现 typing？**  
A：自定义消息（type = 200）属可存储消息，会进入历史消息并出现在会话列表的最新消息展示中。typing 是瞬时状态，必须用不可存储的信令消息（type = 2）。

**Q2：信令消息"不保证送达"，typing 频繁丢失怎么办？**  
A：这是设计取舍而非缺陷。typing 丢失不影响主流程，通过 3s 保活心跳降低感知；真正必须兜底的是"提示残留"，由接收端 10s 超时解决。

**Q3：信令消息会写入历史消息吗？**  
A：不会。信令消息不可存储，双方均无法通过历史消息查询到 typing 记录。这也是选型的首要理由。

**Q4：typing 会占用历史消息存储吗？**  
A：不会。信令消息不可存储，不产生历史消息存储开销；未读数与消息量的计费口径请以官方《计费说明》为准。

**Q5：可以跨端同步 typing 状态吗？**  
A：无需同步。typing 是瞬时状态，各端独立接收展示即可。如需"输入中"这类持久语义的状态表示，应使用用户自定义状态能力（updateUserCustomStatus，2.20.0+，状态长度上限 64 字节、限频 1 次/秒，需开通旗舰版并由技术支持开启用户状态订阅开关），而非 typing 的输入状态。

**Q6：大群（数百人）需要 typing 吗？**  
A：不建议。全量广播会放大信令量且 UI 噪音大，建议 ≤ 50 人群启用。
